# D2S 1차 구현 범위와 완료 기준

> 범위 정정 (2026-10-08): AI Native는 개발팀의 작업 방식이다. 제품 내 AI 요약·매핑·협상 초안 및 모델 API 연계는 사용자 요청에 포함되지 않으며 현재 구현 범위와 합격 기준에서 제외한다. 변경 근거는 저장된 상태·규칙·이력으로 제공한다.

상태: 사용자의 “진행”에 따라 합성 데이터 기반 개발에 착수했다. 제품 AI 항목은 사용자 범위 정정에 따라 제외했다. 구현·시험 결과와 남은 검증은 별도 기록한다.

추가 선택: 사용자가 “명령하면 관계도와 상세 패널을 함께 보여주기”를 선택했다. I07에 [AG-UI 명령 탐색](ag-ui-navigation.ko.md)을 연결한다. 정해진 명령으로 화면을 탐색하며 모델 연결·업무 판단은 포함하지 않는다. 실제 결과는 [실행 검증 기록](d2s-implementation-validation.ko.md)을 따른다.

1차 목표는 모의 서버 500대분의 요구조건·BOM·구성에서 공급사별 협의, 검증, 부분 선정까지 실행하고 결정 근거를 재현하는 것이다. 핵심 검증은 BOM 설정, 공급사별 데이터 분리, 변경 후 상태·수량의 정확성, Extension 재사용이다.

기준 문서는 [기능 명세](server-d2s-functional-spec-v0.1.ko.md), [상태와 행동 명세](d2s-state-actions-and-motion-v0.1.ko.md), [기술 검토](d2s-state-motion-stack-review-v0.1.ko.md)다. Dell의 실제 업무·자료를 검증한 범위나 운영 서비스 출시 범위를 뜻하지 않는다.

## 1 구현이 끝났을 때 가능한 업무

구매기업은 요구조건과 BOM 개정을 발행한다. 같은 프로젝트에서 공급사 A·B와 각각 사양·가격·수량·납기를 협의한다. 설계·품질 담당자는 적용 구성과 근거를 확인해 승인한다. 구매 담당자는 유효한 공급 조건으로 선정안을 만들고 승인자는 현재 가용 물량을 다시 확인해 선정한다.

목표 500대 중 450대분만 선정하면 부족한 50대분의 담당자와 후속 조달 과업을 유지한다. 이후 공급이 감소하면 기존 선정 이력과 현재 부족분을 함께 표시한다. 사용자는 선정 결과에서 요구조건, BOM, 구성, 제안, 검토, 확약의 기준 버전을 찾을 수 있다.

ASD-STE100에서 참고한 용어 일관성, 짧은 문장, 명시적 주체, 조건과 결과의 분리를 적용한다. 한국어 문서의 정식 STE 준수를 주장하지 않는다. 제1원칙에 따라 화면 구조보다 결정에 필요한 데이터·권한·조건을 먼저 고정한다.

## 4 BOM 설정과 Extension의 검증 범위

### BOM 설정

입력 후보는 UTF-8 CSV와 값으로 구성된 단일 시트 XLSX다. 필수 의미는 품목 식별자·개정, 사용 위치 식별자, 부모 사용 위치, 수량·수량 기준, 단위, 적용 구성이다. 같은 부품이 두 위치에 쓰이면 사용 위치를 각각 보존한다. 열 이름이 같아도 다른 의미를 자동으로 합치지 않는다.

| 합성 양식       | 표현 차이                          | 검증할 내용                                         |
| --------------- | ---------------------------------- | --------------------------------------------------- |
| 서버 시스템 BOM | 한국어 열 이름과 부모 사용 위치    | 구성별 계층·수량·옵션의 의미 보존                   |
| 시스템 보드 BOM | 영문 열 이름과 반복 부품 사용 위치 | 같은 부품의 서로 다른 위치를 합치지 않음            |
| 전원 모듈 BOM   | 공급사별 열 이름과 전원 사양·단위  | 공개된 하위 구조·사양만 처리. 단위와 적용 개정 보존 |

세 BOM은 서로 다른 구조를 그대로 보존한다. 공통으로 표현 가능한 소규모 하위 구조를 각 열 형식으로도 작성해 매핑 결과가 같은지 비교한다. 시스템 BOM과 보드 BOM 전체가 동일하다고 가정하지 않는다.

관리자는 지원 필드의 이름·형식·단위·필수 조건, 열 매핑, 열 순서와 공개 범위를 설정한다. 설정 발행 전에 순환, 없는 부모, 중복 사용 위치, 모호한 수량 기준, 알 수 없는 단위를 검사한다. 과거 업무는 발행 당시의 설정 버전으로 재현한다.

병합 셀, 이미지·PDF의 표, 매크로, 수식 실행, 암묵적 들여쓰기만 있는 계층은 첫 입력 범위에서 제외한다. 해당 파일은 변환이 필요하다고 안내한다. 새 객체 의미·특수 계산·새 연계는 Extension 개발 범위로 구분한다.

### 서버 규칙 Extension

첫 패키지는 전원 모듈의 적용 전압, 요구 출력, 구성·개정 호환 조건과 근거 누락을 검사한다. 입력은 버전이 고정된 공개 허용 데이터와 기업 설정이다. 출력은 충족·위반·미검증 판정, 이유, 적용 규칙 버전이다. 모의 규칙은 실제 서버의 전기·열 적합성을 보증하지 않는다.

개발팀이 검토한 규칙 모듈·스키마·검증 사례를 같은 배포물에 포함하고 조직별로 활성화한다. 모듈은 승인된 계약을 사용하며 Core 저장소를 직접 변경하지 않는다. 조직 격리, 필수 감사, 최종 선정 조건은 Extension으로 해제할 수 없다.

재사용 검증은 같은 패키지에 다른 전원 조건과 합성 BOM을 넣어 수행한다. 패키지에는 고객 BOM·가격·공급사·문서를 넣지 않는다. 호환되지 않는 설정의 활성화를 차단하고, 새 패키지·설정 버전이 과거 검토를 바꾸지 않는지 확인한다. 신규 사용을 비활성화해도 기존 결정 근거는 유지한다.

이 검증은 두 합성 기업의 구조 검증이다. 실제 두 번째 고객에서의 재사용, 외부 개발자의 패키지 설치와 공개 마켓플레이스는 후속 범위다.

| 서버 규칙 패키지        | 두 합성 기업에서 같은 패키지 사용. Core 분기 0건. 첫 기업 업무 데이터 포함 0건                        | 패키지 구성, 서로 다른 설정·데이터의 결과, 버전·비활성화 사례 |
| 변경 근거 조회          | 화면의 상태·원인·기준 개정이 권한 있는 저장 기록과 일치. 조회로 상태 변경 없음                        | 역할별 응답과 원본 상태·버전 대조                             |
| 실행과 복구             | 반복 요청의 중복 선정·배분 0건. 재시작 후 저장된 상태·후속 작업 복구. 복원 결과의 선정·이력 일치      | 실패 주입, 재시작, 백업·복원 시험 기록과 운영 절차            |

보안·버전·배분·필수 승인 오류는 평균 점수로 상쇄하지 않는다. 실패한 필수 기준이 있으면 해당 범위를 완료로 표시하지 않는다. 실제 시험을 수행하지 못한 항목은 미검증으로 남긴다.

### 근거 조회와 사용성 평가

변경 근거는 저장된 상태·규칙·검토 기록으로 제공한다. 모델 서비스나 API 키가 필요하지 않다.

핵심 과업의 90% 이상을 프로젝트 공간 이탈 없이 수행하는지 관찰한다. 역할별 참여자 5명 이상 중 80% 이상이 30초 안에 상태·원인·다음 담당자를 찾는 것을 제안 기준으로 사용한다. 실제 참여자 확보 전에는 사용성 성과를 주장하지 않는다.

### 성능 평가

성능은 [기술 검토의 측정안](d2s-state-motion-stack-review-v0.1.ko.md#9-개발-승인-후의-검증-계획)을 따른다. BOM 사용 위치 10,000개·관계 30,000개, 동시 표시 200개 카드·400개 연결, 동시 세션 100개·초당 변경 요청 10개를 합성 목표 부하로 둔다.

장비·네트워크·서버 자원을 고정한 뒤 첫 작업 공간 p95 2초, 로컬 선택 반응 p95 100ms, 다른 참여자 갱신 p95 2초, 60Hz 장비의 모션 프레임 간격 p95 20ms를 측정한다. 이는 개발 후 검증할 목표이며 현재 성능이나 Dell 데이터 규모를 뜻하지 않는다. 초과 원인과 조정 결과를 보고한다.

## 6 개발 순서와 단계 종료 조건

개발 착수 승인에 따라 아래 순서로 진행한다. 화면의 기본 골격은 첫 단계부터 사용하고 실제 상태·권한을 연결하면서 완성한다. 각 단계는 앞 단계의 저장·권한·버전 계약을 사용한다.

| 순서 | 구현 작업                               | 단계 종료 조건                                                                               |
| ---- | --------------------------------------- | -------------------------------------------------------------------------------------------- |
| 1    | I01·I02, I07의 기본 공간과 관계·표 선택 | 두 역할의 별도 세션에서 요구조건·구성을 조회. 허용 데이터만 전송. 저장·재조회·감사 기록 확인 |
| 2    | I03·I04, I07의 요청·협의 패널           | BOM 세 양식을 설정으로 입력. 두 공급사와 개별 요청·제안·역제안·자료 공유 수행                |
| 3    | I05·I06, I07의 상태·부분 선정           | M1–M4 실행. 450대분 선정과 50대분 후속 과업, 변경·감소·만료·동시 배분 검증                   |
| 4    | I09, I07의 모션·갱신·성능 조정          | 두 번째 합성 기업에서 재사용. 모션 감소·키보드·재연결·목표 부하 측정                         |
| 5    | I08·I10과 전체 회귀                     | 근거 조회·권한 평가, 복구 검증, 수용 사례별 결과·실패·미검증 목록 제출                       |

오류·처리시간 기록과 검증은 1단계부터 작업별로 추가한다. 5단계는 전체 증거를 취합하는 시점이다. 공급사 격리와 승인·배분 오류가 발견되면 원인을 수정하고 관련 사례를 다시 실행한 뒤 다음 단계의 완료를 판단한다.

역할은 제품·업무 책임, 기술 책임, 구현 책임, 검증 책임으로 구분한다. 한 사람이 여러 역할을 맡을 수 있다. AI는 문서·구현·검증 초안을 보조하며 사람은 업무 의미, 권한, 승인 조건과 완료 판단을 검토한다. 수용 기준을 통과한 변경의 처리시간·결함·재작업을 측정한다.

달력 기준 일정과 비용은 가용 인력·주당 투입 시간·검토 담당자를 확인한 뒤 산정한다. 현재는 단계 순서와 완료 조건을 확정할 수 있는 수준이다. 실제 고객 자료의 확보는 이 합성 구현의 시작 조건이 아니며, 고객 파일럿의 필수 조건이다.

## 7 기술 선택과 후속 범위

기술 우선안은 [기존 검토서](d2s-state-motion-stack-review-v0.1.ko.md#5-권고-기술-스택)를 유지한다. 화면은 React·TypeScript와 React Flow·Motion, 업무 서버는 NestJS·PostgreSQL, 상태 전이는 안정 배포의 XState, 명령과 갱신은 REST·SSE를 기준으로 구현 계획을 잡는다. BOM·서버 규칙·협의·선정은 모듈 경계를 두고 공통 권한·버전 계약을 사용한다.

정확한 라이브러리 버전과 호환성은 착수 시 확인한다. 첫 개발 환경은 합성 자료를 사용하는 로컬·격리 시험 환경으로 제한하는 안이다. 클라우드, 실제 기업 SSO와 데이터 보관 지역은 사용 조건을 확인해 결정한다.

| 후속 범위                      | 추가하기 전에 필요한 결정                                          |
| ------------------------------ | ------------------------------------------------------------------ |
| 봉인 입찰·경매·역경매          | 적격 참가자, 공개 수준, 마감·연장, 동점, 정정·취소, 장애 복구 규칙 |
| PLM·ERP 실제 연계              | 원본 시스템, 수정 책임, 인증, 중복·부분 실패·복구 계약             |
| GPU·액체 냉각·복잡한 최적 배분 | 실제 구성 규칙과 검증 근거, 계산 규모, 별도 알고리즘 평가          |
| 공개 Extension 마켓플레이스    | 외부 코드 검토·권한·지원 책임, 지식재산권, 배포·업데이트·제거 정책 |
| 복수 공급사의 공동 기술 협의   | 서로에게 공개할 사양·자료·참여 정보와 별도 협의 권한               |
| 실제 운영 서비스               | 고객 보안·호스팅·SSO, 운영 책임, 복구 목표, 지원·비용 기준         |

## 8 개발 착수 전에 확정할 항목

현재 개발 기준은 제품 AI 항목을 제외하고 정정한 I01–I10의 합성 데이터 구현 범위와 합격 기준이다. 아래 모의 업무 정책을 적용한다.

| 모의 정책          | 제안                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| 공급 확약 인정     | 공급사 권한자의 조건 제출 후 구매 담당자가 같은 조건을 확인              |
| 선정안의 물량 선점 | 초안은 선점하지 않음. 최종 승인 시 가용량 재검증과 확정 배분을 함께 처리 |
| 공급 감소·철회     | 운영 가용량에 즉시 반영. 기존 확약·선정 근거는 이력 보존                 |
| 외부 결과 공개     | 내부 선정 승인 후 권한자가 해당 공급사에 별도 게시                       |
| 제품 AI 기능       | 현재 범위에서 제외. AI Native는 개발팀의 작업 방식                       |

사용자가 정한 부분 선정 정책은 이 확인 목록에서 다시 선택하지 않는다. 남은 정책은 실제 고객의 규칙을 대신하지 않는 합성 검증 기준이다. 개발 착수 승인을 받았으며 실제 고객 정책은 별도 검증한다.
