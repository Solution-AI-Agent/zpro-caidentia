# 데이터센터용 서버 SRM 실행 계획

> 범위 정정 (2026-10-08): AI Native는 개발팀의 작업 방식이다. 제품 내 AI 요약·매핑·협상 초안 및 모델 API 연계는 사용자 요청에 포함되지 않으며 현재 구현 범위와 합격 기준에서 제외한다. 변경 근거는 저장된 상태·규칙·이력으로 제공한다.

상태: 사용자의 “진행”에 따라 합성 사례 기반 개발에 착수했다. 제품 AI는 현재 범위에서 제외한다. 현재 구현과 검증 결과는 [실행 검증 기록](d2s-implementation-validation.ko.md)을 따른다. 실제 담당자·자료는 현재 미확보다.

추가 선택: 현재 D2S 화면에 [AG-UI 명령 탐색](ag-ui-navigation.ko.md)을 연결한다. 사용자가 선택한 관계도·상세 패널 동시 열기를 지원하며 모델 API는 사용하지 않는다. 아래 시안·검토 문서의 “검증 전” 표시는 해당 문서 작성 시점을 뜻한다.

기준: [D2S 중심 SRM 기획안](srm-d2s-concept-v0.1.ko.md). 최초 목표 기업은 Dell이며 첫 제품군은 데이터센터용 서버다.

화면 검토 자료: [D2S Core를 중심으로 한 구매기업·공급사 정적 비교 시안](assets/d2s-core-role-comparison-v0.2.png). 첫 시안의 시각적 방향을 유지한 후속 제안이며, 역할별 정보 표시와 D2S 연결을 검토한다. 실제 권한·업무 실행 검증은 아직 수행하지 않았다.

기술 검토 자료: [D2S 상태 관리와 모션 UI의 구현 검토](d2s-state-motion-stack-review-v0.1.ko.md). 상태·관계·계산 현황의 구분, 기술 스택 우선안, 모션 기준과 개발 승인 후의 검증 조건을 정리했다. 문헌·설계 검토 결과이며 실행 검증 전 단계다.

상세 설계 자료: [상태 전이와 화면 행동 명세](d2s-state-actions-and-motion-v0.1.ko.md). 20개 행동의 권한·시작 조건·결과, 부분 선정, 공급 감소 예외, 모션 장면과 15개 수용 사례를 정의했다.

상태·모션 검토 자료: [네 장면의 정적 스토리보드](assets/d2s-state-motion-storyboard-v0.3.png). 조달 충족 300→300→500→450대와 선정 승인 0→0→0→450대를 구분한다. 마지막 장면은 부분 선정 후 부족한 50대분을 별도로 관리한다.

개발 범위 검토 자료: [1차 구현 범위와 완료 기준](d2s-first-implementation-scope-v0.1.ko.md). 합성 데이터를 사용하는 10개 구현 작업, 산출물별 합격 증거, 5단계 개발 순서와 후속 범위를 정의했다. 제품 AI 항목을 제외한 범위로 개발에 착수했다.

현재 합의는 업무 모델, 평가 사례, 데이터 공개 명세와 화면 흐름을 작성하기에 충분하다. 고객 파일럿의 성공 여부는 실제 담당자·자료·기준선으로 검증해야 한다. 작업은 아래 순서로 진행하고, 추가 정보가 필요한 단계에 도달할 때 해당 정보를 확인한다.

이번에 작성한 문서 초안은 A의 설계 산출물이다. B–E가 완료되었거나 고객 요구가 검증되었다는 뜻은 아니다. 문서 간 일관성 검토와 실제 소프트웨어 실행 검증을 구분한다.

현재는 합성 사례로 D를 진행한다. 실제 도입 효과와 Dell 적합성은 미검증으로 유지한다. 이후 담당자·자료가 확보되면 업무 사실과 표본을 확인하고 설계를 수정한다.

## 3 첫 구현 범위의 검토 후보

첫 구현 후보는 한 프로젝트에서 서버의 요구조건·BOM·구성·공급 대안·검증·선정 근거를 연결하는 D2S 흐름이다. 전원 모듈의 공급 차질과 대체안 검토를 추가해 설계·공급 조건이 바뀌어도 연결이 유지되는지 확인한다. 합성 데이터 구현은 착수 승인을 받았으며 실제 고객 배포는 별도 범위다.

[1차 범위 검토안](d2s-first-implementation-scope-v0.1.ko.md)은 주 프로젝트 외에 물량 중복 검증용 보조 프로젝트와 재사용·격리 검증용 두 번째 가상 구매기업을 포함한다. 제품 내 AI 기능은 현재 범위에서 제외했다. 아래 항목의 상세 산출물·의존성·완료 증거는 해당 검토안을 따른다.

| 작업                    | 의존성                                  | 수용 기준                                                                                           |
| ----------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------- |
| D2S 대상과 관계         | 요구조건·BOM·구성·대안·검증·결정의 의미 | 선정 결과에서 최초 요구조건과 각 기준 버전을 추적한다. 공급 대안 제안이 설계 변경 검토로 연결된다.  |
| 업무프로세스 연결       | D2S 대상·버전과 상태 전이 규칙          | 같은 구성에 기술 검토와 견적 협의를 연결한다. 방식이 바뀌어도 D2S 참조와 이전 업무 이력을 유지한다. |
| 상태 변경과 현황 갱신   | 전이 권한·의존 버전·계산 규칙·후속 작업 | 동시 수정·반복 요청·만료·재시작을 검증한다. 늦은 조회 결과가 최신 현황을 덮어쓰지 않는다.           |
| 조직·참여자·공개 범위   | 역할·거래·데이터 소유 명세              | 두 공급사의 서버 응답·검색·파일·이벤트가 격리된다.                                                  |
| BOM 정의와 버전         | 품목·사용 위치·구성 모델                | 세 가지 지원 양식을 설정으로 수용하고 원본 의미를 보존한다.                                         |
| 공급사별 견적 요청·제출 | 프로젝트·BOM·공개 범위                  | 각 제안이 요청 버전과 연결된다. 자사 제안만 편집한다.                                               |
| 변경 영향·기술 검토     | 구성 조건·견적·검증 근거                | 미검증 상태와 추가 검토를 표시한다. 이전 승인 범위를 유지하며 새 구성에는 재검토를 요구한다.        |
| 다회차 협의·대안 비교   | 기술 상태·견적 버전                     | 비용·납기·물량의 조건과 변경 이력을 비교한다.                                                       |
| 선정·배분·감사 기록     | 승인 조건·구성별 공급 계산              | 선정의 BOM·제안·기술 승인·상업 조건을 재현한다.                                                     |
| 공유 작업 공간          | 위 업무 객체와 권한                     | 같은 선택 맥락에서 흐름·영향·대화·다음 행동을 연결한다.                                             |
| 모션과 관계도 성능      | 상태별 표현·표시 범위·시험 환경         | 선택·변경 경로를 표현한다. 모션 감소 설정에서도 같은 과업을 수행한다. 확정 전 완료 표시가 없다.     |
| Extension 검증          | Core 계약·고객 설정·샘플 요구           | 서버 전용 규칙을 Core 분기 없이 적용한다. 두 번째 가상 조직 검증과 독립 고객 검증을 구분한다.       |
| 변경 근거 조회          | 권한·기준 개정·검토 기록                | 저장된 상태·규칙·이력과 화면의 근거가 일치하는지 검사한다.                                          |

봉인 입찰·역경매는 별도 대표 사례와 규칙을 정의해 구현 순서를 정한다. 일반 협상과 실시간 경매의 완료 조건을 섞지 않는다. GPU·액체 냉각의 상세 규칙, 다계층 공급망, 공개 Extension 마켓플레이스의 도입 순서는 첫 흐름의 검증 결과로 결정한다.

초기 데이터 연결은 정해진 파일 교환 형식으로도 검증할 수 있다. 실제 PLM·ERP 연결이 첫 도입의 필수 조건인지 확인한 뒤 연계 범위를 결정한다. 파일 교환 검증을 실제 시스템 연계 완료로 보고하지 않는다.

| PLM·ERP의 원본과 수정 책임    | 객체별 입출력 계약 초안 작성                | 실제 연계 개발 전                                             | 고객 시스템 책임자                  |

팀원 이름과 외부 담당자를 임의로 배정하지 않는다. 정보가 없으면 해당 단계의 결과를 가정·미검증으로 표시하며, 독립적으로 가능한 작업을 계속한다.

## 5 AI Native 작업 방식

- 제품 책임자는 우선순위와 고객 가치를 결정한다. 도메인 검토자는 설계·구매·품질의 의미와 승인 조건을 확인한다.
- 기술 책임자는 데이터·권한·연계·운영 설계를 검토한다. 검증 책임자는 수용 사례의 기대 결과와 실제 결과를 비교한다. 한 사람이 여러 책임을 맡을 수 있다.
- AI는 요구사항·화면·코드·검증 사례·문서의 초안을 작성한다. 사람이 책임지는 업무 결정을 대신 승인하지 않는다.
- 작업마다 `요구사항 → 산출물 → 검증 사례 → 결과`를 연결한다. 실패 사례를 회귀 검증에 추가한다.
- 측정 대상은 검토를 포함한 작업 시간, 결함 유출, 재작업, 운영·모델 비용이다. AI 사용률을 성과 목표로 삼지 않는다.

## 6 다음 검토의 결정 항목

다음 검토에서는 [1차 구현 범위와 완료 기준](d2s-first-implementation-scope-v0.1.ko.md)을 기준으로 포함 기능, 합격 증거, 개발 순서와 모의 업무 정책을 확인한다. 부분 선정 정책과 상태·모션 방향은 기존 합의를 유지한다. 구현 범위 합의와 개발 착수 승인은 구분한다.

합성 자료로 시작하는 결정은 실제 데이터가 도착했을 때 모델을 검증할 필요를 없애지 않는다. 구현 범위를 합의할 때 성공 기준, 필수 예외, 사용할 데이터, 고객 시스템과의 경계, 팀 가용성을 함께 확인한다.
