# D2S 상태 전이와 화면 행동 명세

상태: 개발 전 검토 초안. 사용자의 명시적인 개발 착수 승인은 아직 받지 않았다. 문서와 정적 그림만 작성한다.

목적: D2S 대상의 상태가 바뀌는 조건, 변경 권한, 관계·현황의 계산, 화면 행동을 연결한다. 기준은 [기능 명세](server-d2s-functional-spec-v0.1.ko.md)와 [상태·모션·스택 검토](d2s-state-motion-stack-review-v0.1.ko.md)다.

모든 품목·물량·정책은 모의 설계용이다. Dell의 실제 정책이나 업무를 확정한 내용이 아니다. 기술 스택은 앞선 검토의 우선안을 유지하며, 이 문서는 업무 규칙을 구체화한다.

## 1 검토 중인 정책

| 항목 | 초안의 처리 | 확정 상태 |
|---|---|---|
| 협업 범위 | 구매기업이 A·B 공급사와 각각 협의한다. | 사용자 확정 |
| 설계와 소싱의 관계 | 기술 협의·견적·승인은 D2S 대상과 버전을 참조한다. | 사용자 확정 |
| 공급 확약 인정 | 공급사 권한자가 기간·물량·조건을 제출하고 구매 담당자가 동일 조건을 확인하면 인정한다. | 모의 정책 제안 |
| 공급 감소·철회 | 감소한 물량은 운영상 가용량에서 즉시 제외한다. 기존 약속과 선정은 이력으로 보존한다. | 모의 정책 제안 |
| 일부 물량 선정 | 조건을 충족한 물량을 먼저 선정하고 잔여 부족분·후속 담당자를 관리한다. | 사용자 확정 |
| 역할 겸임 | 역할별 권한을 구분하고 겸임 허용 여부는 기업 정책으로 정한다. | 실제 고객 확인 필요 |
| 선정 결과 공개 | 내부 승인 후 공개 권한자가 해당 공급사에 결과를 게시한다. | 모의 정책 제안 |

부분 선정에서도 기술·품질 승인, 선택 물량에 적용되는 유효 제안, 공급 확약, 가용 배분은 필수 조건으로 유지한다. 미검증 부품을 선정 완료로 바꾸지 않는다. 선정한 물량과 남은 부족분의 책임자를 기록한다.

## 2 상태와 판단을 구분한다

| 구분 | 표시 값 | 변경 방식 |
|---|---|---|
| 요구조건 개정 | 초안·검토 중·발행·대체됨 | 책임자의 발행·변경 행동 |
| 구성 스냅샷 | 초안·검토 중·승인·대체됨 | 설계 담당자의 검토 요청·승인 |
| 기술 검토 | 미검토·검토 중·승인·반려 | 지정된 기술 검토자의 결정 |
| 품질 검토 | 미검토·검토 중·승인·반려 | 지정된 품질 검토자의 결정 |
| 제안 버전 | 초안·제출·협의·최종 제안·철회 | 공급사의 제출과 구매기업의 협의 |
| 공급 조건 | 제안·확인 요청·확약 제출·확약·변경 통보·철회·만료 | 공급사의 제출·통보와 구매기업의 조건 확인 |
| 선정안 | 작성 중·승인 요청·승인·반려·인계 | 구매 담당자와 선정 승인자의 행동 |
| 공개 결과 | 미게시·게시·정정 게시 | 공개 권한자의 대상별 게시 |
| 관계의 적용 가능성 | 미검증·적용 가능·부적합·재검토 필요 | 요구조건·구성·부품·근거·규칙 버전에서 계산 |
| 현황 | 확인된 충족 수량·부족 수량·다음 행동·갱신 상태 | 유효한 원본과 정책에서 계산 |

제안의 유효 기간은 제출 상태와 별개다. 제출 상태가 유지되어도 기간이 지나면 현재 선정에 사용할 수 없다. 검토 완료와 승인도 구분한다. 반려된 검토 역시 완료된 업무이며, 승인 조건은 충족하지 않는다.

승인 기록의 유효성은 적용 범위로 판단한다. C1-A에서 승인한 부품을 C1-B에 자동 적용하지 않는다. 과거 승인 이후 새 요구조건이 생기면 새 범위에 대한 검토를 만든다.

## 3 공통 처리 규칙

상태 변경 요청은 행동, 대상 식별자, 예상 버전, 제출 자료, 요청 식별자를 포함한다. 서버는 사용자·조직·협의 범위·현재 상태·필수 조건을 검증한다.

- 같은 요청 식별자가 재전송되면 기존 결과를 반환한다.
- 예상 버전과 현재 버전이 다르면 변경을 저장하지 않고 다시 확인하도록 안내한다.
- 여러 대상에 걸친 승인·배분은 관련 조건을 한 트랜잭션에서 보호한다.
- 상태·근거·이력·후속 작업을 함께 저장한다.
- 외부 알림과 현황 계산은 재시도 가능한 후속 작업으로 처리한다.
- 수신 권한이 있는 참여자에게만 변경을 전달한다.
- 만료 여부는 승인 시각에 다시 확인한다.
- 확정 상태는 서버 응답 이후에 표시한다.

새 자료 제출은 새 버전이나 검토 회차를 만든다. 제출된 견적, 완료된 검토, 승인된 선정 결과의 내용을 덮어쓰지 않는다.

## 4 행동과 상태 전이

아래 표의 변경 권한은 해당 프로젝트·협의 범위에서 그 역할이 부여된 사용자에게만 적용한다.

| ID | 행동과 권한 | 시작 조건 | 저장 결과와 다음 행동 |
|---|---|---|---|
| T01 | 요구조건 발행 · 요구조건 책임자 | 필수 조건·단위·근거·적용 범위가 정의됨 | 요구조건 개정을 발행하고 연결된 구성의 검토 기준으로 사용 |
| T02 | 구성 검토 요청 · 설계 담당자 | BOM 참조와 선택 옵션이 식별되고 구조 검사가 통과됨 | 검토할 스냅샷을 고정하고 기술·품질 과업 생성 |
| T03 | 요청 패키지 발행 · 구매 담당자 | 공유할 사양·수량·기간·공개 대상이 정해짐 | 공개 사양과 요청 버전을 고정. 미승인 구성은 검토용임을 표시 |
| T04 | 제안 제출 · 해당 공급사 | 자사에 발행된 유효 요청이며 필수 제안 항목이 충족됨 | 제안 버전 보존. 기술 검토와 상업 협의에 연결 |
| T05 | 기술 검토 시작 · 기술 검토자 | 대상 구성·부품·요구조건의 버전과 과업 배정 확인 | 검토 중으로 전환. 필요한 근거의 누락 표시 |
| T06 | 기술 승인 또는 반려 · 기술 검토자 | 최신 검토 범위와 근거 확인. 승인 시 필수 기술 조건 충족 | 범위가 고정된 결정 기록. 품질·상업 상태는 독립적으로 유지 |
| T07 | 품질 승인 또는 반려 · 품질 검토자 | 적용 부품·구성의 필수 품질 증거 확인 | 품질 결정 기록. 설계 승인·선정 조건을 다시 계산 |
| T08 | 구성 승인 · 설계 담당자 | 필수 기술·품질 조건과 BOM·옵션 검증 충족 | 해당 구성 승인. 공급 확약이 없으면 조달 충족 수량 유지 |
| T09 | 공급 확약 제출 · 공급사 권한자 | 품목 개정·요청 버전·물량·기간·유효 조건이 식별됨 | 확약 제출로 기록하고 구매기업의 조건 확인 요청 |
| T10 | 공급 조건 확인 · 구매 담당자 | 제출한 확약 조건이 요청·협의 결과와 일치하며 유효함 | 확약 상태로 전환. 적용 가능한 구성과 가용량으로 현황 재계산 |
| T11 | 선정안 승인 요청 · 구매 담당자 | 선택 물량의 필수 조건과 선정 정책 충족 | 참조 버전·계획 물량·평가 근거를 고정해 승인 요청. 초안 물량은 확정 배분으로 세지 않음 |
| T12 | 선정안 승인 · 선정 승인자 | 승인 시점에도 필수 조건·유효 버전·가용 물량·정책이 충족됨 | 선정 기록과 배분을 함께 확정. 결과 공개는 미게시 상태 유지 |
| T13 | 선정안 반려 · 선정 승인자 | 검토 대상과 반려 이유 확인 | 반려 기록 보존. 구매 담당자가 수정 회차 작성 |
| T14 | 선정 결과 게시 · 공개 권한자 | 승인된 선정 기록과 수신 조직 확인 | 해당 공급사에 공개할 결과 버전 게시. 다른 공급사의 선정 내역은 포함하지 않음 |
| T15 | 선정 결과 인계 · 구매 담당자 | 승인·공개·인계 대상과 필요한 조건 확인 | 결정 스냅샷을 인계 기록에 연결. 실제 연계 성공 여부는 별도 기록 |
| T16 | 구성 변경 검토 · 설계 담당자 | 변경 이유와 영향받는 요구조건·사용 위치 식별 | 새 구성과 검토 생성. 기존 구성·견적·승인 유지 |
| T17 | 공급 감소·철회 통보 · 공급사 권한자 | 해당 확약의 변경 내용과 적용 시점 식별 | 감소분의 운영 가용량을 제외하고 영향·차질 표시. 기존 선정 삭제 금지 |
| T18 | 공급 물량 증가 확인 · 공급사와 구매 담당자 | 증가분의 조건을 새 버전으로 제출하고 확인 | 확인된 증가분부터 가용량 반영 |
| T19 | 제안 만료 처리 · 시스템 | 유효 시각 경과 | 현재 선정 가능 여부를 갱신. 과거 선정의 참조 제안은 보존 |
| T20 | 참여 권한 철회 · 권한 관리자 | 조직·협의 범위와 철회 권한 확인 | 새 조회·수정·전송 차단. 공개 범위에 맞게 열린 화면 갱신 |

기술·품질 검토는 승인 전의 고정된 구성 스냅샷에서도 진행한다. 구성 승인 후에만 검토를 시작하도록 하면 승인 조건이 순환한다. 요청 패키지와 기술 협의도 설계 확정 전부터 진행할 수 있다.

검사 통과만으로 사람의 승인을 생성하지 않는다. 새 기술 제안이 제출되어도 발행된 요청이나 승인된 구성을 자동 수정하지 않는다.

## 5 공급 감소와 배분의 예외

신규·증액 배분은 처리 시점의 가용 물량을 초과할 수 없다. 그러나 이미 배분한 뒤 공급사가 물량을 줄이면 기존 배분 합계가 새 가용량을 초과할 수 있다. 시스템은 이 사실을 저장하고 예외로 관리한다.

예를 들어 A의 기존 확약 1,000개를 모두 배분한 뒤 확약이 600개로 줄면, 기존 선정은 유지하고 400개의 배분 초과를 표시한다. 현재 조달 충족은 600개를 기준으로 계산한다. 추가 배분은 차단하고 구매 담당자에게 재배분·대체 조달을 요청한다. 공급 감소 기록을 거부하거나 과거 선정 수량을 조용히 줄이지 않는다.

이 검증은 시스템에 등록된 동일 공급 출처와 구매기업의 프로젝트 배분을 대상으로 한다. 공급사가 다른 기업에 한 비공개 약속까지 자동으로 검증할 수 있다고 가정하지 않는다. 같은 물량을 여러 확약 번호로 중복 등록하지 않도록 공급 출처 식별 규칙이 필요하다.

계획·예약·확정 배분은 구분한다. 초기에는 선정 초안이 물량을 선점하지 않는 안을 제안한다. 최종 승인 시 가용량을 다시 확인하고 확정 배분을 만든다. 예약이 필요하면 만료·해제 규칙을 가진 별도 상태로 추가한다.

## 6 계산과 완료 기준

이 사례에서 A와 B는 각각 동일 부품 두 개가 한 서버에 필요하다. 서로 다른 부품을 한 서버에 혼용할 수 없다. 나머지 필수 부품은 500대분 있다고 가정한다.

각 공급원의 인정 물량은 해당 기간의 유효한 공급량에서 다른 프로젝트의 유효 배분을 제외한다. 현재 프로젝트의 확정 배분은 이 프로젝트의 조달 충족에 계속 포함한다. 기술·품질·구성의 필수 승인을 충족하지 못한 대안은 확인된 충족 계산에서 제외한다.

조달 충족 대수는 A 물량을 2로 나눈 내림값과 B 물량을 2로 나눈 내림값을 합산하되, 목표 500대와 다른 필수 부품의 확보 대수로 제한한다.

| 유효한 A 물량 | 유효한 B 물량 | 확인된 충족 | 이유 |
|---:|---:|---:|---|
| 600개 | 0개 | 300대 | B는 미검증 또는 미확약 |
| 600개 | 400개 | 500대 | 두 구성이 승인되고 기간·공급·가용량 조건 충족 |
| 600개 | 300개 | 450대 | B 100개는 다른 프로젝트에 배분 |
| 601개 | 399개 | 499대 | A는 300쌍, B는 199쌍. 남은 서로 다른 모듈을 혼용하지 않음 |

자료가 없으면 미확인으로 표시한다. 확인된 충족 수량에서 제외했다는 이유로 실제 공급 불가능이 입증되었다고 표현하지 않는다.

선정 완료와 프로젝트 완료도 구분한다. 한 공급사의 선정이 승인되어도 전체 목표의 부족분은 남을 수 있다. 프로젝트의 선정 완료는 필요한 물량의 선정 승인과 나머지 필수 조건이 모두 충족되어야 표시한다.

| 정책 모드 | 유효 물량이 450대분일 때 | 전체 현황 |
|---|---|---|
| 부분 선정 허용 · 확정 | 조건을 충족한 물량만 승인 가능. 부족 50대분의 후속 책임·계획을 기록 | 일부 선정·목표 미충족 |

조달 충족 대수와 선정 승인 대수를 각각 표시한다. 전자는 현재 유효한 구성·공급·가용량으로 계산한다. 후자는 승인한 선정 기록의 배분으로 계산한다. 500대분을 조달할 수 있어도 선정 승인이 없다면 선정 승인 대수는 0대다. 선정 후 공급이 감소하면 승인 이력과 현재 조달 부족을 함께 표시한다.

정책 모드가 바뀌어도 과거 승인에 적용한 정책 버전은 보존한다. 진행 중 선정안의 기준을 바꾸려면 영향과 재확인 절차를 기록한다.

## 7 구매기업과 공급사의 화면 행동

같은 요청 버전을 선택한 상태에서 역할별 행동을 제공한다. 아래 상태는 공급사 B에 연결된 범위의 예다.

| 상황 | 구매기업의 표시와 행동 | 공급사 B의 표시와 행동 |
|---|---|---|
| 자료 보완 필요 | 해당 검토의 누락 근거 확인, 보완 요청 작성 | 공개된 보완 요청 확인, 자사 자료 제출 |
| 기술·품질 검토 중 | 내부 담당자·검토 상태 확인, 권한에 따른 결정 입력 | 공개된 검토 상태 확인, 추가 자료 제출 |
| 구성 승인·공급 확약 대기 | 확약 요청과 조건 확인. 전체 충족 300대 표시 | 자사 400개 제안과 확약 요청 확인. 전체 목표 수량은 제공하지 않음 |
| 공급 조건 확인 완료 | 전체 충족 500대 표시, 선정안 작성 | 자사 확약 확인 완료와 선정 결과 대기 표시 |
| 선정 승인·미게시 | 승인 근거 확인, 해당 공급사에 결과 게시 | 게시 전에는 내부 선정 결과·평가가 표시되지 않음 |
| 결과 게시 | 게시 버전·수신 범위 확인 | 자사 선정 결과와 공개 조건 확인 |
| 재검토 필요 | 영향받는 요구조건·구성·제안 확인, 검토 회차 생성 | 공개된 변경 사양·보완 요청만 확인 |
| 다른 참여자가 먼저 수정 | 최신 버전과 차이 확인 후 다시 요청 | 자사 공개 범위의 최신 자료로 다시 확인 |
| 현황 갱신 지연 | 기준 시각·갱신 중 표시, 서버에서 승인 조건 재확인 | 공개 범위의 기준 시각·갱신 중 표시 |

공개하지 않은 내부 사유를 설명하기 위해 공급사 화면에 경쟁사 이름·활동·물량·승인 단계 수를 노출하지 않는다. 공급사에게 필요한 공개 상태와 다음 행동을 별도로 정의한다.

## 8 정적 모션 스토리보드

검토 그림: [네 장면의 상태·모션 정적 시안](assets/d2s-state-motion-storyboard-v0.3.png). [생성·수정 프롬프트](assets/d2s-state-motion-storyboard-v0.3.prompt.txt)를 함께 보관한다. 그림은 모의 구매기업 관점이며 실제 공급사 화면의 공개 범위를 뜻하지 않는다.

같은 구매기업 화면에서 PSU-B를 계속 선택한 채 네 장면을 비교한다. M1–M3에는 유효한 제안이 제출되었고 아직 선정 승인은 없다고 가정한다. M4에서는 B의 가용 물량이 300개로 줄고, 이 수량에 적용되는 유효한 상업 조건을 다시 확인한 뒤 부분 선정한다. 실제 애니메이션의 성능은 이 그림으로 검증할 수 없다.

| 장면 | 원본 상태 | 현황과 다음 행동 | 모션 지시 |
|---|---|---|---|
| M1 검토 중 | 구성·기술·품질 검토 중, 공급 확약 대기 | 충족 300/500대. 기술·품질 검토 진행 | 선택 카드·경로 강조 150–250ms. 검토 패널을 같은 위치에 표시 |
| M2 검토 완료 | 구성·기술·품질 승인, 공급 확약 대기 | 충족 300/500대 유지. 공급 확약 확인 | 승인 배지를 150–250ms 전환. 미완료 공급 조건을 짧게 강조 |
| M3 확약 확인 | 구성·기술·품질 승인, B 400개 확약·가용 확인 | 충족 500/500대. 선정안 작성. 선정 승인은 아직 없음 | 확정 응답 후 수치를 500으로 교체하고 관련 경로를 1회 강조 |
| M4 부분 선정 | B 100개가 다른 프로젝트에 배분됨. A 600개·B 300개의 조건을 재확인하고 선정 승인 | 조달 충족 450/500대, 선정 승인 450/500대. 부족 50대분·구매 담당자의 후속 조달 과업 유지 | 현재 가용량과 승인 수량을 각각 갱신. 남은 부족분을 짧게 강조 |

M2에서 기술·품질의 승인만으로 충족 수량을 500대로 바꾸면 불합격이다. M3에서 선정 승인을 자동 완료로 표시해도 불합격이다. M4의 부분 선정 뒤 전체 프로젝트를 완료로 표시하면 불합격이다.

모션을 줄이는 설정에서는 이동과 경로 효과를 축소하고 같은 값·상태·다음 행동을 제공한다. 화면을 확대하거나 다른 노드를 선택하는 동작은 사용자가 시작한다. 새 사건마다 화면 위치를 자동 이동시키지 않는다.

색상은 상태의 보조 표현이다. 진행 중, 조치 필요, 조건 위반, 승인 상태를 텍스트·아이콘으로 함께 표시한다. 승인 배지가 있어도 현황 갱신 중이면 그 사실을 별도 표시한다.

## 10 제한된 실행 검증의 착수 후보

착수 후보는 구매기업 한 곳과 공급사 두 곳, 한 서버 프로젝트, 한 전원 모듈 대체 그룹이다. 요구조건·구성·제안·검토·확약·선정 기록을 연결한다. 구매기업 내부의 설계·품질·구매·선정 권한을 구분한다.

동일한 의미를 가진 자료를 합의한 세 BOM 템플릿으로 받아 코드 변경 없이 매핑·검증한다. 관계도와 표는 같은 선택 대상을 유지한다. M1–M4의 모션과 C01–C15의 상태·권한 사례를 검증한다. 성능은 앞선 검토서의 합성 부하와 고정한 시험 환경으로 측정한다.

첫 검증의 산출물은 작동하는 제한 범위, 상태·권한 시험 결과, 성능 측정, 실패 사례다. 이를 검토해 실제 고객 연계와 첫 제품 범위를 결정한다. 이 문서의 작성과 정적 시안 검토는 개발 착수 승인을 대신하지 않는다.

[1차 구현 범위와 완료 기준](d2s-first-implementation-scope-v0.1.ko.md)에 구현 작업·의존성·산출물별 합격 증거와 개발 순서를 정리했다. 기존 상태·수량·공개 정책의 기대 결과는 그대로 유지한다.
