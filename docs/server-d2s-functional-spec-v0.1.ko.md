# 데이터센터용 서버 D2S 기능 명세 초안

> 범위 정정 (2026-10-08): AI Native는 개발팀의 작업 방식이다. 제품 내 AI 요약·매핑·협상 초안 및 모델 API 연계는 사용자 요청에 포함되지 않으며 현재 구현 범위와 합격 기준에서 제외한다. 변경 근거는 저장된 상태·규칙·이력으로 제공한다.

목적: 서버의 설계 의도·요구조건·BOM·구성·공급 대안·검증·선정 근거를 D2S Core로 연결하고, 기술 협의·견적·협상·승인 업무가 그 위에서 실행되는 기준을 정의한다. 전원 모듈의 공급 차질은 이 연결을 검증하는 대표 사례다.

기준: [기획안](srm-d2s-concept-v0.1.ko.md)과 [실행 계획](srm-d2s-execution-plan.ko.md). 아래의 기업, 품목, 수량, 규칙은 모두 설계 검토용 합성 사례다. Dell의 BOM·정책·공급 상태를 나타내지 않는다.

모의 사례로 시작하기로 합의했다. 실제 담당자·BOM·견적 사례는 현재 미확보이므로 기능 명세와 초기 화면 검토에는 이 합성 사례를 사용한다.

D2S가 솔루션의 Core라는 방향과 구매기업·공급사 한 곳씩 개별 협의하는 초기 범위는 확정했다. 아래 세부 객체·규칙·평가 수치는 논의용 명세다. 실행형 프로토타입을 포함한 개발은 사용자의 명시적인 승인 후 착수한다.

상태·관계·현황의 계산과 모션 구현은 [상태 관리와 기술 스택 검토](d2s-state-motion-stack-review-v0.1.ko.md)에 구체화했다. 해당 문서의 수치는 실행 검증을 위한 제안 조건이다.

세부 동작은 [상태 전이와 화면 행동 명세](d2s-state-actions-and-motion-v0.1.ko.md)에 정의했다. 초기에는 조건을 충족한 물량의 부분 선정을 허용하고 잔여 부족분·후속 담당자를 관리하기로 확정했다.

## 1 대표 사례와 기대 결과

구매기업 `BUYER-DEMO`는 기간 D까지 가상 서버 `S-RACK-DEMO` 500대에 필요한 부품을 조달하려 한다. 기준 설계는 `C1`, BOM 개정은 `R1`이다. 서버 한 대에는 동일한 승인 전원 모듈 2개가 필요하다. 서로 다른 전원 모듈을 한 서버에 혼용할 수 없다는 가상 규칙을 둔다.

요구조건 `REQ-PWR-01 v1`은 위 전원 모듈 구성 규칙을 정의한다. 요구조건을 R1의 전원 사용 위치와 C1-A·C1-B 구성에 연결한다. 공급사 B에게 공개한 사양은 `SP-PSU-01 v1`, 요청은 `RFQ-B-01 v1`로 식별한다. 구매기업과 B는 이 공개 사양과 요청 버전을 함께 확인한다. 내부 전체 BOM과 전체 수량은 B에게 전달하지 않는다.

신규 설계 사례는 `요구조건 정의 → 임시 BOM·구성 수립 → 공급사 기술 제안 → 구성별 검증 → 선정 근거 확정`으로 검토한다. 기술 검토와 상업 협의는 필요한 조건을 갖춘 시점에 병렬로 실행한다. 공급사의 제안이 설계를 바꾸면 새 구성 버전과 검토를 만든다. 아래 공급 차질 사례는 이 D2S 흐름 중 공급 조건이 바뀐 상황이다.

R1의 전원 대체 그룹에 `PSU-A`와 후보 `PSU-B`를 연결한다. 실제 적용안은 A를 선택한 `C1-A`와 B를 선택한 `C1-B` 스냅샷으로 구분한다. A의 구성은 승인되어 있고 B의 구성은 추가 기술·품질 검토가 필요하다. B가 승인되어도 A의 과거 구성과 승인 기록을 덮어쓰지 않는다. 구매기업은 같은 프로젝트에서 A·B와 각각 협의한다. 두 공급사의 참여 공간·자료·대화는 분리한다.

| 입력 | 합성 값 | 해석 |
|---|---|---|
| 목표 서버 수량 | 500대 | 구매기업 내부의 전체 목표다. 공급사에는 각자에게 공개한 요청 범위만 제공한다. |
| 서버 한 대의 전원 모듈 | 2개 | 같은 승인 품목으로 한 쌍을 구성한다. |
| A의 기간 D 내 확약 | 최초 1,000개, 지연 통보 후 600개 | 변경된 확약과 이전 버전을 보존한다. |
| B의 기간 D 내 제안 | 400개 | 공급 조건 확약과 기술 승인을 각각 확인해야 한다. |
| 그 밖의 필수 부품 | 500대분 확보 | 계산을 제한하기 위한 명시적 가정이다. 실제 사례에서는 각 필수 부품을 확인한다. |

| 상태 | 기대 결과 |
|---|---|
| A 지연 전 | A의 1,000개로 500대분을 충족한다. |
| A 지연 후, B 미검증 | 확인된 600개로 300대분을 충족한다. 부족분은 200대다. B는 미검증 대안으로 표시한다. |
| B의 구성·기술·품질 승인과 공급 확약 완료 | A 600개와 B 400개를 각각 쌍으로 배분하면 총 500대분을 충족한다. 두 구성의 적용 부품을 구분한다. 선정 승인은 별도다. |
| B의 400개 중 100개가 다른 프로젝트에 배정됨 | B의 가용분은 300개로 150대분이다. 합계는 450대분이며 부족분은 50대다. |
| B의 납기가 D 이후임 | 기간 D의 충족 대수에 B를 포함하지 않는다. 향후 대안으로 별도 표시한다. |

위 값은 부품 조건에 따른 조달 충족 대수다. 생산능력·조립·시험·출하 일정은 별도 확인 대상이다. 미확약 물량을 포함한 시뮬레이션은 ‘가정 포함’으로 구분하며 확인된 물량과 합산해 확약으로 표시하지 않는다.

## 2 역할과 결정 책임

| 역할 | 주요 행동 | 결정 책임 |
|---|---|---|
| 구매 담당자 | 견적 요청, 가격·납기 협의, 대안 비교, 선정안 작성 | 상업 조건과 공급 계획 |
| 설계 담당자 | 서버 구성·요구 조건 정의, 변경 영향·기술 적합성 검토 | 적용 구성과 설계 조건 |
| 품질 담당자 | 공급사·부품 자격과 시험 증거 검토 | 품질 검증과 승인 범위 |
| 선정 승인자 | 필요한 승인과 조건을 확인하고 선정안 승인 | 선정과 배분의 최종 결정 |
| 공급사 담당자 | 공개된 사양 확인, 자사 제안·증거·공급 조건 제출 | 자사 제안의 정확성과 확약 |
| 설정 관리자 | BOM 양식·검증·화면·업무 설정 관리 | 설정의 발행과 버전 관리 |

사용자가 여러 역할을 겸임할 수 있는지는 기업 정책으로 정한다. 설정 관리자라는 이유로 모든 견적·원가를 읽는 권한을 자동 부여하지 않는다.

## 3 업무 객체와 연결

이 표는 논리 모델이다. 데이터베이스 종류·테이블·구현 프레임워크를 확정하지 않는다.

설계 요구조건·BOM·구성·공급 대안·검증·선정의 관계는 D2S Core가 유지한다. 업무프로세스는 대상과 기준 버전을 참조하고 자신의 담당자·상태·결과를 관리한다. 프로세스 종료 후에도 D2S 관계와 결정 근거를 조회할 수 있어야 한다.

| 객체 | 식별과 주요 정보 | 필수 관계·조건 |
|---|---|---|
| 조직·참여자 | 조직, 사용자, 역할, 유효 기간 | 데이터 소유 조직과 거래 참여 권한을 구분한다. |
| 프로젝트 | 소유 조직, 제품·구성, 목표 기간·물량 | 공급사 초대와 공개 범위를 명시한다. |
| 설계 의도·요구조건 | 목적, 요구 값·조건, 근거, 책임자, 버전 | 요구조건을 충족할 구성·BOM 위치와 검증 근거를 연결한다. 공개 사양의 원본 관계를 보존한다. |
| 품목·개정 | 소유 조직의 품목 식별자, 제조사 참조, 개정 | 서로 다른 조직의 같은 번호를 자동 병합하지 않는다. |
| BOM 개정·사용 위치 | 부모·자식, 사용 위치, 수량·단위, 옵션 | 순환 관계를 거부한다. 사용 위치의 조건을 품목 속성과 분리한다. |
| 구성 스냅샷 | BOM 개정, 선택 옵션, 적용 기간·조건 | 발행된 업무는 특정 스냅샷을 참조한다. 모든 선택지를 동시에 사용한 것으로 계산하지 않는다. |
| 공급 대안 | 적용 구성, 부품 개정, 공급 출처, 제안·검증 참조 | 동일 부품의 다른 공급 조건과 다른 부품의 구성 변경을 구분한다. 후보와 승인 대안을 구분한다. |
| 검증 근거 | 적용 요구조건·구성·부품 개정, 증거, 규칙 버전, 책임자 | 조건 검사와 사람의 승인을 구분한다. |
| 공급사별 요청 패키지 | 수신 조직, 공개된 사양·BOM 부분, 요청 조건, 버전 | 내부 전체 BOM과 분리된 공개 범위를 갖는다. |
| 제안 버전 | 공급사, 요청 버전, 품목·가격·수량·단위·납기·유효 기간 | 제출 후 내용을 덮어쓰지 않는다. 수정 제안은 이전 버전과 연결한다. |
| 공급 확약·배분 | 공급 출처, 적용 기간, 물량, 확약 상태, 프로젝트별 배분 | 같은 물량을 여러 프로젝트에서 중복 사용하지 않는다. |
| 기술·품질 검토 | 구성·품목 개정, 증거, 결과, 승인자 | 승인 범위를 새 구성·개정으로 자동 확대하지 않는다. |
| 선정 기록 | 선택 제안, 구성, 배분, 승인·조건 스냅샷 | 결정 당시의 근거와 기준 버전을 재현한다. |
| 대화·업무 이벤트 | 대상 객체·버전, 작성자, 공개 대상 | 기술 질의와 상업 협상, 내부 검토의 공개 범위를 구분한다. |
| 업무프로세스 실행 | 방식, D2S 대상·기준 버전, 참여자, 상태, 결과 | D2S 안에서 실행하는 기술 협의·견적·협상·승인은 공통 대상을 참조한다. 방식 변경 시 이전 실행을 보존하고 새 실행과 연결한다. |
| 설정·Extension 버전 | 스키마·매핑·규칙·화면, 호환 Core, 요청 권한 | 업무 데이터와 배포 패키지를 분리한다. |

## 4 독립적으로 관리할 상태

| 구분 | 상태 | 전이 규칙 |
|---|---|---|
| 요청 | 초안 → 발행 → 마감 또는 취소 | 발행 시 기준 구성과 공개 범위를 고정한다. 변경하면 새 요청 버전을 만든다. |
| 제안 | 초안 → 제출 → 협의 → 최종 제안 또는 철회 | 각 제출을 버전으로 보존한다. 유효 기간이 지난 제안을 현재 유효 제안으로 취급하지 않는다. |
| 조건 검사 | 미검증 → 충족 또는 위반 | 자료가 없거나 충돌하면 미검증이다. 검사 결과는 근거·규칙 버전을 참조한다. |
| 기술·품질 승인 | 미검토 → 검토 중 → 승인 또는 반려 | 권한자만 승인한다. 변경 영향이 있으면 새 범위에 대한 검토를 만든다. |
| 공급 조건 | 제안 → 확인 요청 → 확약 또는 철회·만료 | 조건·물량·기간의 변경 이력을 남긴다. |
| 선정 | 작성 중 → 승인 요청 → 승인 → 인계 | 필수 기술·품질 승인, 유효 제안, 공급 조건, 배분 검사를 충족해야 승인한다. 반려된 안은 수정·재요청하며 인계하지 않는다. |

기술 검토와 상업 협의는 동시에 진행할 수 있다. 최종 선정은 필요한 조건을 모두 충족해야 한다. C1의 승인은 과거 기록으로 보존하며, C2에 자동 적용하지 않는다. 변경이 기존 승인의 어느 부분에 영향을 주는지 명시한다.

대상·업무의 원본 상태, 관계의 적용 가능 여부, 화면에 표시하는 계산 현황을 분리한다. 공급 대안의 사용 가능 여부는 특정 구성·부품 개정·요구조건·기간에 대해 판정한다. 과거 승인 기록이 보존되어 있어도 새 구성에 대한 승인은 재검토가 필요할 수 있다.

상태 변경은 권한 있는 업무 행동으로 요청한다. 서버가 현재 상태·의존 버전·필수 근거를 확인하고 상태·이력·후속 작업을 함께 저장한다. 지도·집계는 갱신 상태와 기준 시각을 표시한다. 선정 승인과 배분은 현재 원본을 다시 검증한다.

## 5 요구사항과 수용 사례

| ID | 요구사항 | 검증 방법·기대 결과 | 기획안 연결 |
|---|---|---|---|

## 6 데이터 공개와 행동 권한

기본 정책은 명시적으로 허용한 데이터와 행동만 제공하는 것이다. 구매기업 소속이라는 사실만으로 전체 데이터 접근을 허용하지 않는다. 각 사용자의 담당 프로젝트와 역할을 함께 확인한다.

초기에는 구매기업과 공급사 한 곳으로 협의 범위를 구성한다. 한 조직에서 여러 담당자가 참여할 수 있다. 구매기업은 A·B와 각각 협의하며, 공급사끼리의 직접 대화와 공동 열람은 초기 범위에 포함하지 않는다. 승인된 공통 사양은 적용 대상 공급사에게 각자의 요청 패키지로 배포한다.

| 정보 | 구매 담당자·선정 승인자 | 설계·품질 담당자 | 공급사 A | 공급사 B |
|---|---|---|---|---|
| 전체 목표·구성·영향 지도 | 담당 범위 | 담당 범위 | 공개한 요청 부분만 | 공개한 요청 부분만 |
| 내부 목표원가·평가 메모 | 별도 권한 필요 | 기본 접근 없음 | 접근 없음 | 접근 없음 |
| A의 가격·상업 협상 | 해당 업무 권한 | 기본 접근 없음 | 자사 권한 | 접근 없음 |
| B의 가격·상업 협상 | 해당 업무 권한 | 기본 접근 없음 | 접근 없음 | 자사 권한 |
| A의 기술 제안·시험 증거 | 해당 업무 권한 | 해당 기술 검토 권한 | 자사 권한 | 접근 없음 |
| B의 기술 제안·시험 증거 | 해당 업무 권한 | 해당 기술 검토 권한 | 접근 없음 | 자사 권한 |
| 승인된 공통 사양·공개 답변 | 담당 범위 | 담당 범위 | 적용 대상일 때 | 적용 대상일 때 |
| 전체 공급 충족 대수·경쟁사 배분 | 해당 업무 권한 | 업무상 허용한 범위 | 접근 없음 | 접근 없음 |

권한 명세에는 읽기, 작성, 제출, 공유, 승인, 내보내기를 구분한다. 공급사는 자기 제안만 수정·제출한다. 설계·품질 담당자는 부여받은 검토를 승인한다. 선정 승인자는 최종 선정안을 승인한다. 정책 변경 권한과 업무 데이터 읽기 권한은 별개다.

내부 또는 특정 공급사 자료를 공통 답변으로 공개하려면 공개 권한자가 내용과 대상을 검토한다. 파생 데이터는 원본의 공개 제한을 유지한다. 경쟁사의 존재·개수·실시간 활동도 임의로 표시하지 않는다.

프로토타입의 역할 전환은 각 역할의 경험을 설명하는 기능이다. 실제 격리 검증에서는 별도 인증 맥락과 서버 응답을 사용한다. 화면에서 값을 숨긴 것만으로 SEC-01을 통과했다고 평가하지 않는다.

## 7 공유 화면의 업무 흐름

프로젝트 공간의 중심에는 요구조건→BOM·구성→공급 대안→검증→선정 근거의 D2S 지도를 둔다. 각 연결은 업무 의미와 기준 버전을 가진다. 사용자는 한 대상을 선택한 상태에서 연결된 프로세스를 실행한다. 권한이 있는 정보에 한해 다음 영역을 연결한다.

1. 상단에 선택한 제품·요구조건·구성·공개 사양의 버전과 주요 미해결 사항을 표시한다.
2. 중앙에 요구조건, 구성의 부품 사용 위치, 공급 대안, 검증 근거, 선정 결과의 연결과 변경 영향을 표시한다.
3. 선택한 대상에 기술 협의·견적·협상·승인 업무를 연결하고 각각의 상태와 다음 담당자를 표시한다.
4. 같은 공간의 패널에서 대안별 검사·승인 상태와 비용·납기·공급 조건을 비교한다.
5. 대상과 기준 버전에 연결된 대화·결정을 표시한다. 작성 전에 공개 대상을 확인할 수 있게 한다.
6. 변경 근거는 접근 가능한 상태·규칙·검토 기록을 표시한다. 권한자가 다음 행동을 선택한다.

구매 담당자는 공급 지연을 열고 300대 충족·200대 부족을 확인한다. B의 미검증 대안을 선택하면 필요한 검토와 담당자를 본다. 설계·품질 승인과 공급 확약이 완료되면 같은 위치에서 500대 충족 안을 비교한다. 공급사 B는 자신에게 요청한 품목·수량·검증·협의만 확인한다.

추가 비교 패널과 대화는 선택 맥락을 유지한다. 실제 관찰에서는 화면 이동뿐 아니라 클릭·스크롤·이해 시간도 측정한다.

정적 시안의 평가 기준은 두 역할의 공개 사양·요청 버전이 일치하고, 검토자가 요구조건에서 선정 근거까지의 연결을 설명할 수 있는 것이다. 다음 행동과 담당자는 30초 안에 찾도록 목표를 둔다. 이 단계에서는 화면 이해도를 평가하며 실제 데이터 격리나 상호작용 성능을 통과했다고 보고하지 않는다.

## 8 고객 확인이 필요한 항목

- 전원 모듈 부족과 대체안 검토가 실제 초기 사용 조직의 중요한 문제인지 확인한다.
- 실제로 사용하는 BOM 양식·구성 규칙과 공개 가능한 사양·자료 범위를 확인한다.
- 기술·품질·상업 승인자의 역할과 겸임 가능 여부를 확인한다.
- ‘공급 가능’과 ‘확약’의 업무 의미, 기간·수량·배분의 원본 시스템을 확인한다.
- 설계 변경 시 어떤 승인과 협의를 다시 수행하는지 확인한다.
- 기존 절차의 소요 시간·재입력·재검토 사례로 성과 기준선을 정한다.

이 확인은 합성 사례의 구조 검토와 별개다. 고객이 다른 사례를 우선하면 공통 객체와 권한 원칙을 유지하면서 대표 흐름과 수용 기준을 수정한다.
