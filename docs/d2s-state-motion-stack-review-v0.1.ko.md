# D2S 상태 관리와 모션 UI의 구현 검토

> 범위 정정 (2026-10-08): AI Native는 개발팀의 작업 방식이다. 제품 내 AI 요약·매핑·협상 초안 및 모델 API 연계는 사용자 요청에 포함되지 않으며 현재 구현 범위와 합격 기준에서 제외한다. 변경 근거는 저장된 상태·규칙·이력으로 제공한다.

검토일: 2026-10-08

**현재 기획은 구현 가능하다. D2S의 대상·관계·버전을 저장하고, 업무별 상태를 독립적으로 관리하며, 화면 현황을 그 결과에서 계산하는 구조를 제안한다.** 모션은 서버가 확정한 변화와 사용자가 선택한 탐색 경로를 표현한다.

이 판단은 공식 기술 문서와 현재 명세를 대조한 설계 검토 결과다. 제품 구현, 성능 측정, 실제 Dell 데이터 검증은 아직 수행하지 않았다. 실행형 프로토타입을 포함한 개발은 사용자의 명시적인 승인 후 착수한다.

기준: [D2S 기획안](srm-d2s-concept-v0.1.ko.md), [기능 명세](server-d2s-functional-spec-v0.1.ko.md), [정적 비교 시안](assets/d2s-core-role-comparison-v0.2.png).

## 1 권고안과 적용 전제

첫 구현의 우선안은 **React·TypeScript·Vite, React Flow, Motion, NestJS, XState, PostgreSQL**이다. 프런트엔드·API·작업 처리기를 하나의 저장소에서 관리한다. 백엔드는 D2S, 업무, 권한, 설정의 경계를 가진 하나의 애플리케이션으로 구성한다. API와 작업 처리기는 같은 업무 코드를 사용하며 별도 프로세스로 실행할 수 있다.

선정 기준은 상태·권한의 정확성, 관계도의 표현력, 모션 성능, 변경을 검토하기 쉬운 코드 구조, 초기 운영 부담이다. 다음 전제에서 가장 균형이 좋은 안으로 판단한다.

- 첫 제품은 인증 후 사용하는 데스크톱 중심 B2B SaaS다.
- 기존 개발팀의 필수 언어와 고객 지정 클라우드는 아직 정해지지 않았다.
- 고객별 BOM은 공통 의미와 설정으로 수용한다.
- 초기 협업은 구매기업과 공급사 한 곳씩 개별 협의한다.
- 대량 BOM 전체를 한 화면에 동시에 펼치는 요구는 없다.
- AI Native는 개발팀의 작업 방식이다. 제품 내 모델 기능은 초기 범위에 포함하지 않는다.

기존 조직의 Java·.NET 표준, 고객의 전용 배포 조건, 실제 데이터 규모가 확인되면 해당 경계를 다시 평가한다. 현재 단계에서 절대적인 최적 성능이나 최저 운영비를 입증한 것은 아니다.

| 기능 | 구현 판단 | 설계의 핵심 |
|---|---|---|
| 요구조건부터 선정까지의 관계 지도 | 가능 | 대상·관계의 종류, 기준 버전, 적용 조건을 저장한다. |
| 기술·품질·상업 협의의 병렬 진행 | 가능 | 업무별 상태를 분리하고 선정 조건에서 결합한다. |
| 변경 영향과 재검토 표시 | 가능하나 업무 정의가 중요 | 영향 규칙과 적용 범위를 명시하고 불명확하면 미검증으로 남긴다. |
| 고객별 BOM 설정 | 정한 지원 범위에서 가능 | 공통 의미를 유지하면서 필드·단위·매핑·검증을 설정한다. |
| 같은 화면의 공급사별 공개 | 가능하나 서버 검증 필요 | 데이터를 반환하기 전에 대상·관계·필드·파생 정보를 통제한다. |
| 관계와 현황에 연결된 모션 | 가능 | 표시 범위를 제한하고 선택·변경에 반응하는 모션을 사용한다. |
| 대규모 BOM의 화면 성능 | 측정 필요 | 서버 조회 범위와 화면 표시 범위를 각각 제한한다. |
| 실제 Dell 업무 적합성 | 고객 검증 필요 | 실제 BOM, 승인 정책, 원본 시스템, 성과 기준선을 확인한다. |

## 2 상태를 세 종류로 구분한다

### 대상과 업무의 원본 상태

D2S 대상과 업무 실행은 각각 상태를 가진다. 아래 전이는 대표 경로이며, 재제출·반려·철회도 별도 사건으로 기록한다.

| 대상 | 대표 상태 | 상태의 책임 |
|---|---|---|
| 요구조건 개정 | 초안 → 검토 중 → 발행 → 대체됨 | 요구조건 책임자 |
| BOM·구성 개정 | 초안 → 검토 중 → 승인 → 대체됨 | 설계 권한자 |
| 기술 검토 | 미검토 → 검토 중 → 승인 또는 반려 | 해당 구성의 기술 검토자 |
| 품질 검토 | 미검토 → 검토 중 → 승인 또는 반려 | 품질 검토자 |
| 견적·협상 | 초안 → 제출 → 협의 → 최종 제안 또는 철회 | 공급사와 구매 담당자 |
| 공급 확약 | 제안 → 확인 요청 → 확약 → 철회 또는 만료 | 공급사 제출과 구매기업 확인 정책 |
| 선정안 | 작성 중 → 승인 요청 → 승인 → 인계 | 선정 승인자 |

기술 승인이 완료되어도 품질 검토와 가격 협의는 계속될 수 있다. 이를 하나의 진행 상태 값으로 합치지 않는다. 조건 검사 결과인 충족·위반·미검증도 사람의 승인과 별도로 보존한다.

병렬 상태와 조건부 상태 전이는 이미 정립된 상태 기계 개념이다. 이 제품에서는 상태별 허용 행동과 승인 조건을 명세하는 데 적용한다. [W3C SCXML](https://www.w3.org/TR/scxml/#parallel), [XState 병렬 상태](https://stately.ai/docs/parallel-states)

### 관계의 적용 상태

관계는 양쪽 대상을 연결하는 선 이상의 정보를 가진다. 관계 종류, 양쪽 대상의 정확한 개정, 적용 구성, 기간·수량 조건, 근거, 공개 범위를 함께 관리한다.

| 관계 예 | 저장하거나 계산할 내용 |
|---|---|
| 요구조건 → 구성 | 어느 요구조건 개정을 어떤 구성으로 충족하려는가 |
| 구성 → BOM 사용 위치 | 어떤 부품 개정을 몇 개 사용하며 어떤 옵션에서 적용하는가 |
| 공급 대안 → 구성 | 이 대안이 해당 구성에서 후보인지, 검증되었는지, 사용 가능한가 |
| 검증 근거 → 요구조건·구성 | 어떤 개정·조건·규칙을 검사하고 승인했는가 |
| 제안·확약 → 공급 대안 | 어느 요청 버전, 기간, 물량, 공급 출처에 대한 약속인가 |
| 선정 → 구성·제안·승인 | 결정 당시 어떤 버전과 근거를 사용했는가 |

관계의 등록 상태와 현재 적용 가능 여부를 구분한다. 예를 들어 과거 승인 기록은 승인 상태로 보존한다. 새 구성에 대한 적용 가능 여부는 재검토 필요로 표시할 수 있다. 부품 전체에 전역 승인 표시 하나를 두면 이 차이를 잃는다.

BOM의 부모·자식 관계는 순환을 허용하지 않는다. 설계 피드백은 새 개정·검토로 연결한다. 영향 탐색은 관계 종류와 방문한 대상·버전을 기록해 반복 탐색을 끝낸다. 관계도에 표시되는 모든 연결을 같은 방향·규칙으로 자동 전파하지 않는다.

### 화면에 표시하는 계산 상태

화면의 선정 가능 여부, 부족 물량, 병목, 다음 담당자는 원본 상태·관계·규칙에서 계산한다. 사용자가 이 값을 직접 완료로 바꾸지 못하게 한다.

예를 들어 특정 제안의 선정 조건은 유효한 적용 구성, 필수 기술·품질 승인, 유효 제안, 해당 기간의 공급 조건, 배분 제약, 선정 정책으로 평가한다. 자료가 없거나 조건이 충돌하면 충족으로 판정하지 않는다.

프로젝트 전체 목표 충족 여부와 개별 제안의 선정 가능 여부는 별도다. 초기에는 조건을 충족한 물량의 부분 선정을 허용하고, 잔여 부족분·후속 담당자를 관리하기로 사용자와 확정했다. 목표 수량 충족만으로 공급사 선정이 자동 승인되지 않는다. 실제 고객 적용 시에는 해당 기업의 정책을 확인한다.

계산 결과에는 기준 구성·규칙 버전, 사용한 원본 버전, 계산 시각, 갱신 상태를 둔다. 재계산 중인 결과는 이전 확정 결과와 구분한다. 과거 시점의 화면은 당시의 선정 근거를 조회하는 용도로 표시한다.

## 3 상태 변경은 업무 행동으로 요청한다

사용자는 승인, 반려, 제안 제출, 확약 철회처럼 업무 의미가 있는 행동을 요청한다. 상태 값을 직접 지정하는 범용 수정 기능은 제공하지 않는다.

처리 순서는 다음과 같다.

1. 서버가 사용자·조직·협의 범위와 요청 행동의 권한을 확인한다.
2. 현재 상태, 요청의 기준 버전, 필요한 근거, 관련 대상의 버전을 확인한다.
3. 허용된 상태 전이와 업무 조건을 평가한다.
4. 현재 상태·새 업무 기록·감사 이력·후속 작업을 같은 데이터베이스 트랜잭션으로 저장한다.
5. 작업 처리기가 영향 현황을 다시 계산하고, 수신 권한이 있는 사용자에게 변경을 알린다.
6. 화면이 권한에 맞는 최신 현황을 받아 모션으로 변화를 표현한다.

동시 승인이나 물량 배분은 관련 자료를 보호하는 잠금 또는 직렬화·재시도로 검증한다. 대상 한 건의 버전 확인만으로 여러 공급 확약의 중복 배분을 막았다고 판단하지 않는다. 의존 자료가 변경되면 승인 조건을 다시 평가한다. 신규·증액 배분은 현재 가용량 안에서 처리한다. 선정 후 공급 감소로 발생한 배분 초과는 과거 선정을 보존하면서 예외로 기록한다.

같은 제출이 반복되어도 결과를 한 번만 반영하도록 요청 식별자를 둔다. 외부 알림·연계는 재시도 가능한 작업으로 처리하며, 수신 측 중복 처리도 방지한다. 변경 이력과 작업 생성은 함께 저장하고, 작업 실패는 재시도·실패 목록으로 관리한다.

견적 만료는 시각 조건을 읽을 때도 검사한다. 만료 작업의 실행이 늦어졌다는 이유로 만료 견적을 승인하지 않는다. 장기 대기·마감 시각·재시도 상태는 데이터베이스에 저장한다. 브라우저 타이머나 서버 메모리에만 의존하지 않는다.

## 4 모의 사례로 확인한 논리와 검증할 결과

이 표는 설계 단계에서 대조한 기대 결과다. 실행 시험 통과 실적은 아니다. 기존 사례와 같이 동일한 승인 PSU 두 개가 서버 한 대에 필요하고, 그 밖의 필수 부품은 500대분 있다고 가정한다.

| 사건 | 원본 상태와 관계의 처리 | 화면의 기대 결과 |
|---|---|---|
| A의 확약이 1,000개에서 600개로 감소 | 기존 확약 버전을 보존하고 새 공급 조건을 반영 | 300대분 충족, 200대분 부족 |
| B가 400개를 제안 | B의 구성·기술·품질 검토와 공급 확약을 각각 대기 상태로 연결 | B는 후보로 표시하고 충족 대수는 300대 유지 |
| B의 구성·기술·품질 승인만 완료 | 해당 구성에 유효한 승인 관계를 연결 | 공급 확약이 없으므로 300대 유지 |
| B의 400개가 기간 D 내 확약되고 모두 가용 | 승인 구성과 유효 확약·가용 배분을 함께 확인 | 500대분 충족. 최종 선정 승인은 별도 유지 |
| B의 확약 중 100개가 다른 프로젝트에 배정 | 동일 공급 물량의 가용분을 300개로 계산 | 300 + 150 = 450대분, 부족 50대 |
| B의 납기가 D 이후로 변경 | 기간 D의 계산에서 B의 물량 제외 | 기간 D에는 300대분 충족 |
| B 부품의 개정이나 적용 구성이 변경 | 이전 승인은 보존하고 새 적용 범위에 검토 생성 | 새 범위는 재검토 필요. 영향 없는 A의 승인 유지 |
| 두 사용자가 같은 잔여 물량을 동시에 배분 | 하나의 유효 물량 범위에서 직렬화하거나 충돌 후 재시도 | 총 배분이 확약 가용량을 초과하지 않음 |
| 승인 후 공급 확약 철회 | 과거 선정 기록 보존, 현재 공급 계획에 차질 표시 | 기존 선정 이력과 현재 재조달 필요를 함께 표시 |
| 견적 만료 작업이 지연 | 승인 요청 시 실제 유효 시각을 재확인 | 만료 견적으로 선정 승인 불가 |
| 갱신 알림이 누락되거나 순서가 바뀜 | 개정·변경 순서를 대조하고 필요 시 최신 현황 재조회 | 오래된 현황이 최신 결과를 덮어쓰지 않음 |

조달 충족 대수는 생산·조립·시험·출하 보장을 뜻하지 않는다. 복잡한 다중 대체품 조합이나 여러 프로젝트의 최적 배분은 단순 합계와 별도 알고리즘이 필요하다. 초기에는 명시한 구성과 배분을 검증하고, 최적화는 독립 Extension 후보로 둔다.

### 이 조합을 선택한 이유

관계도·표·패널·모션을 React 계열로 구성하고, 프런트엔드와 서버가 TypeScript의 공통 계약을 사용하도록 제안한다. 이 선택은 데이터 형식과 변경 영향을 함께 검토하기 쉽게 하려는 설계 판단이다. AI가 생성한 코드의 품질 향상을 자동 보장한다는 뜻은 아니다.

shadcn/ui의 컴포넌트 소스를 제품의 디자인 규칙에 맞춰 관리한다. 공통 컴포넌트와 모션 토큰의 변경을 검토해 화면마다 다른 동작이 생기지 않게 한다. [shadcn/ui 공식 설명](https://ui.shadcn.com/docs)

인증 후의 상호작용 중심 앱을 전제로 Vite와 별도 API를 선택했다. Next.js도 이 제품을 구현할 수 있다. 향후 서버 렌더링이나 공개 콘텐츠가 주요 요구가 되면 다시 비교한다. 현재는 업무 API·작업 처리·권한 경계를 명확히 유지하는 데 우선순위를 둔다. [Vite 공식 가이드](https://vite.dev/guide/), [NestJS 모듈](https://docs.nestjs.com/modules)

React Flow는 관계도를 구성하고, ELK.js는 배치 계산을 맡는다. 레이아웃 계산과 매번 발생하는 상태 갱신을 분리한다. 노드 선택·승인 결과 변경만으로 전체 지도를 다시 정렬하지 않는다. React Flow 공식 문서도 큰 트리의 부분 표시와 복잡한 스타일·애니메이션의 비용을 설명한다. [관계도 성능](https://reactflow.dev/learn/advanced-use/performance), [배치 방식](https://reactflow.dev/learn/layouting/layouting)

ELK.js는 작업 스레드 지원을 제공한다. 배치 요청에도 버전을 부여해 늦게 끝난 계산이 현재 선택 상태를 덮어쓰지 않도록 한다. [ELK.js 공식 저장소](https://github.com/kieler/elkjs)

서버 데이터 캐시는 TanStack Query에 맡긴다. 선택한 노드·열린 패널 등 화면 상태는 별도로 관리한다. 화면용 캐시와 XState를 업무 상태의 독립된 원본으로 사용하지 않는다. [TanStack Query 개요](https://github.com/TanStack/query/blob/main/docs/framework/react/overview.md)

XState는 상태 정의와 전이 계산에 사용한다. PostgreSQL 저장, 동시성 제어, 만료 작업, 외부 처리의 재시도까지 별도로 설계한다. 상태 정의를 바꾸면 기존 업무의 정의 버전을 유지하거나 명시적으로 전환한다. 확인 시점의 공식 문서는 v6 alpha를 포함하므로, 초기 제품은 검증한 안정 배포로 고정하고 alpha 전용 기능을 기본 전제로 삼지 않는다. [상태 영속화와 주의점](https://stately.ai/docs/persistence), [공식 릴리스](https://github.com/statelyai/xstate/releases)

PostgreSQL은 재귀 조회와 순환 탐지를 제공한다. 따라서 관계도라는 이유만으로 별도 그래프 저장소를 도입할 필요는 없다. 이는 초기 선택이며 실제 관계 밀도·조회 지연을 측정해 판단한다. Drizzle은 트랜잭션을 명시적으로 제어하는 코드 경계에 사용한다. [PostgreSQL 재귀 조회](https://www.postgresql.org/docs/current/queries-with.html), [Drizzle 트랜잭션](https://orm.drizzle.team/docs/transactions)

pg-boss는 기존 데이터베이스 트랜잭션 안에서 작업을 생성하는 기능을 제공한다. 이를 사용해 상태 저장과 후속 작업 등록을 함께 처리한다. 작업 재시도와 외부 호출의 중복 방지는 애플리케이션에서도 검증한다. SSE는 서버에서 브라우저로 상태 변경을 알리는 용도에 적합하다. [pg-boss](https://github.com/timgit/pg-boss), [NestJS SSE](https://docs.nestjs.com/techniques/server-sent-events)

### 도입을 보류할 기술과 재검토 조건

배포는 컨테이너, 관리형 PostgreSQL, 객체 저장소를 기본 구조로 둔다. 클라우드 사업자·리전·전용 환경 여부는 Dell 또는 첫 고객의 조건을 확인해 결정한다. 기존 업무의 정확성 시험을 통과한 범위에서 비용과 성능을 비교한다.

## 6 모션 설계

목표는 사용자가 상태 변화의 위치와 이유를 이해하면서 화면의 완성도를 느끼게 하는 것이다. 기존 정적 시안의 색상과 공간 구조를 유지하고 깊이·연결·변화를 모션으로 표현한다.

아래 시간과 동시 표시 수는 최초 조정값이다. 실제 사용자 관찰과 장비 측정 후 확정한다.

| 상황 | 표현 | 최초 조정값 | 완료 조건 |
|---|---|---|---|
| 부품·대안 선택 | 선택 카드의 깊이 변화, 관련 경로 강조, 옆 패널 등장 | 150–250ms | 선택 위치와 키보드 초점을 유지 |
| 관계 펼치기 | 기존 위치를 최대한 유지하며 새 관계 등장 | 200–350ms | 관계를 따라갈 수 있고 드래그·입력을 막지 않음 |
| 변경 영향 확인 | 변경 시작점에서 영향 경로를 따라 짧은 강조 이동 | 400–700ms, 1회 | 영향받은 대상과 재검토 이유를 텍스트로도 확인 |
| 승인·확약 완료 | 상태 배지 전환과 관련 현황의 교체 | 150–250ms | 서버 확정 이후에만 완료 표시 |
| 대안 비교 | 선택안과 후보안의 차이를 같은 위치에서 겹쳐 비교 | 200–300ms | 가정·미검증·확정 상태가 계속 구분됨 |
| 검토 요청 도착 | 해당 카드에 짧은 강조와 미처리 표시 | 1–2회 후 정지 | 읽기·입력 중인 위치를 이동시키지 않음 |

Motion은 React의 상태와 연결한 레이아웃·진입·퇴장·SVG 애니메이션을 지원한다. 이 기능을 패널과 선택된 경로에 적용할 수 있다. [Motion for React](https://motion.dev/docs/react)

노드 위치는 React Flow가 관리하고, 노드 내부 내용의 모션은 별도 요소에 적용한다. 두 도구가 같은 요소의 위치 변환을 동시에 제어하지 않게 한다. 상태 변경마다 화면을 자동 확대하거나 전체 노드를 재배치하지 않는다.

한 번에 강조하는 범위를 처음에는 카드 10개·연결 20개 이내로 제안한다. 큰 영향 집합은 그룹과 개수로 요약하고 선택 시 펼친다. 숫자·가격·충족 대수는 확정 값으로 교체한다. 실제 값이 아닌 중간 숫자를 승인 결과처럼 보여주지 않는다.

사용자가 모션 감소를 선택하면 이동·확대 효과를 줄이고 동일한 정보와 행동을 제공한다. 상태는 색상과 함께 아이콘·텍스트로 표시한다. 실제 과업의 키보드 사용과 초점 유지도 확인한다. [Motion 접근성](https://motion.dev/docs/react-accessibility)

## 7 현황 갱신과 데이터 공개

화면 갱신은 즉시성 목표를 두지만 승인·배분의 정확성과 분리해 설계한다. 지도·집계는 후속 작업으로 갱신할 수 있다. 최종 승인 요청은 서버의 현재 상태와 유효 조건을 다시 검사한다.

변경 통지에는 순서·대상 버전·조회 기준을 둔다. 클라이언트는 오래된 결과를 버리고 누락 시 다시 조회한다. 서로 다른 계산 시점의 노드·관계·집계를 섞어 확정 현황으로 표시하지 않는다. 갱신 중에는 기준 시각을 표시하며 서버 검증으로 승인 조건을 재확인한다.

여러 API 인스턴스의 화면 갱신 신호에는 PostgreSQL 알림을 보조적으로 사용할 수 있다. 알림에는 비공개 업무 내용을 담지 않고, 실제 자료는 저장된 변경 기록과 권한 검사로 조회한다. 재연결과 알림 누락은 이 기록으로 복구한다. SSE 연결의 유지 신호, 프록시 버퍼링·시간 제한, 재연결 이후 재인증도 실행 검증에 포함한다. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)

구매기업이 여러 공급사와 협의해도 각 협의 공간의 공개 대상을 구분한다. 서버가 공개 가능한 노드·관계·필드로 화면 자료를 구성한 뒤 전송한다. 숨긴 노드의 개수나 배치가 공급사 화면에 드러나지 않도록 공개 범위 안에서 레이아웃을 계산한다.

PostgreSQL의 행 수준 정책을 조직·거래 경계의 추가 보호로 사용한다. 필드·첨부파일·계산 결과의 공개 통제는 서버의 응답 작성과 저장소 접근에도 적용한다. RLS 우회 권한이 있는 역할과 테이블 소유자는 별도로 취급해야 한다. [PostgreSQL 행 수준 정책](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

실행 계정의 데이터베이스 권한, 요청별 조직 맥락, 연결 풀의 맥락 초기화, 작업 처리기의 조직 맥락을 함께 검증한다. SSE 구독·재연결·전송 시에도 공개 권한을 확인한다. 권한 철회 후에는 새 전송을 차단하고 열려 있는 화면의 자료를 정리한다. 이미 수신하거나 내려받은 정보가 회수된다고 보장하지 않는다.

캐시 키에는 조직·협의 공간·역할 또는 정책 버전·조회 버전을 포함한다. 공급사별 자료를 공통 캐시로 섞지 않는다. 파일 접근도 자료 개정과 공개 대상을 확인한다.

## 8 No-code와 AI Native의 적용 범위

JSON Schema와 Ajv는 필드 형식·허용 값·조건부 필수 항목을 검증하는 데 사용한다. 계층 순환, 단위 의미, 구성 호환성, 승인 정책은 별도의 업무 규칙으로 검사한다. JSON Schema만으로 D2S 의미 검증이 끝난다고 판단하지 않는다. [조건부 스키마](https://json-schema.org/understanding-json-schema/reference/conditionals), [Ajv 시작 가이드](https://ajv.js.org/guide/getting-started.html)

관리자는 지원하는 필드·단위·매핑·조건·검토 단계를 설정한다. 설정 발행 전에는 누락·충돌·도달 불가능한 상태·완료 불가능한 경로를 검사한다. 필수 권한·감사·선정 조건은 고객 설정으로 우회할 수 없게 한다. 실행 중 업무는 사용한 설정·상태 정의 버전을 유지한다.

새 객체 의미, 특수 알고리즘, 새로운 연계는 Extension 개발 범위로 구분한다. 재사용 패키지는 고객의 실제 BOM·가격·공급사 자료와 분리한다.

상태 판정과 수량 계산은 검증 가능한 규칙을 사용한다. 개발팀은 AI를 코드·문서·검증 초안에 활용할 수 있으며, 제품 동작은 명시된 상태·권한 규칙으로 검증한다.

제품 내 모델 서비스 연계와 모델 선정은 현재 범위에 포함하지 않는다. 개발팀의 도구 선택은 제품 런타임의 의존성과 구분한다.

## 9 개발 승인 후의 검증 계획

### 상태와 권한의 필수 통과 조건

| ID | 검증 사례 | 합격 기준 |
|---|---|---|
| F1 | 병렬 상태와 선정 조건 | 기술·품질·견적·확약 상태를 독립적으로 재현. 미충족 조건이 있으면 해당 선정 승인 차단 |
| F2 | 개정 변경과 근거 추적 | 이전 승인을 보존하고 영향 있는 새 범위의 재검토를 식별. 선정에서 모든 기준 버전 추적 |
| F3 | 공급 계산과 동시 배분 | 300·500·450대 사례와 기간 제외를 재현. 신규·증액의 가용량 초과 승인 0건. 선정 후 공급 감소에 따른 부족·배분 초과는 누락 없이 표시 |
| F4 | 반복·지연·순서 변경 | 반복 제출은 한 번만 반영. 오래된 화면 결과의 덮어쓰기와 만료 견적 승인이 없음 |
| F5 | 장애·재시작 | 저장된 상태와 후속 작업을 복구. 누락·실패 작업을 식별하고 재시도 |
| F6 | 공급사별 공개 | 정의한 API·지도·표·파일·SSE·검색·내보내기 사례에서 비공개 데이터 노출 0건 |
| F7 | 설정 변경 | 대표 BOM 세 양식을 코드 변경 없이 수용. 발행한 업무의 설정·상태 정의 버전 재현 |
| F8 | 모션과 업무 수행 | 모션 사용·감소 설정에서 같은 결과. 입력·초점 유지. 서버 확정 전 완료 표시 0건 |

### 성능과 사용성의 최초 측정안

초기 합성 부하를 프로젝트당 BOM 사용 위치 10,000개와 관련 연결 30,000개로 제안한다. 관계도는 한 번에 최대 200개 카드·400개 연결을 보여주고 나머지는 그룹으로 접는다. 이는 Dell의 실제 데이터 규모가 아니다. 100개 동시 세션과 초당 10개 상태 변경 요청을 최초 측정 조건으로 제안한다.

개발 승인 후 시험 장비·브라우저·네트워크·API·DB 자원을 고정하고 기록한다. 더 작은 표본부터 측정해 병목을 확인하며, 아래 수치는 제품 성능을 보장하는 약속이 아니다.

| 항목 | 제안 목표 | 측정 조건 |
|---|---|---|
| 첫 작업 공간 표시 | p95 2초 이내 | 인증 완료 후 권한 있는 첫 부분 그래프·현황 표시 |
| 선택과 패널의 첫 반응 | p95 100ms 이내 | 이미 받은 자료 범위. 추가 자료 조회 시간은 별도 |
| 다른 참여자 화면의 갱신 | 저장 확정부터 p95 2초 이내 | 정상 연결과 정한 부하. 느린 상태는 갱신 중으로 표시 |
| 관계 모션의 프레임 간격 | 60Hz 장비에서 p95 20ms 이내 | 표시·강조 범위를 고정한 대표 동작 |
| 상태 이해 | 역할별 5명 이상 중 80%가 30초 안에 상태·원인·다음 행동 식별 | 모의 사용자 관찰과 실제 고객 관찰 결과를 구분 |
| 근거 재현 | 정의한 선정 사례 100% | 현재 화면과 과거 결정의 기준 버전 대조 |

목표를 충족하지 못하면 먼저 표시 범위, 관계 조회, 계산 범위, 재렌더링, 배치 계산, 이벤트 묶음을 조정한다. 그 결과로 렌더러·저장소·작업 처리 구조의 변경을 판단한다. 전체 BOM의 원본 크기와 동시에 화면에 표시하는 크기를 같은 지표로 취급하지 않는다.

## 10 다음 단계의 산출물

| 순서 | 산출물 | 완료 조건 |
|---|---|---|
| 개발 전 | 상태 사전과 전이표 | 상태의 의미·변경 권한·시작 조건·종료 조건·예외가 정의됨 |
| 개발 전 | 관계·버전·계산 명세 | 적용 범위, 변경 영향, 조달 계산, 선정 조건이 모의 사례와 일치 |
| 개발 전 | 상태별 정적 화면과 모션 설계표 | 선택·변경·검토·완료·실패·갱신 지연을 표현하고 공개 범위를 명시 |
| 개발 승인 후 | 제한된 실행 검증 | 한 요구조건·구성, 두 공급사와의 개별 협의, 상태·동시성·권한·모션 시험 |
| 검증 결과 확인 후 | 첫 구현 범위와 운영 계획 조정 | 측정 결과로 규모·일정·클라우드·고객 연계 범위를 확정 |

부분 선정 허용과 잔여 부족분 관리는 초기 정책으로 확정했다. 공급 확약의 인정 조건과 승인 범위의 개정 단위는 모의 정책을 구체화해 검토한다. [상태 전이와 화면 행동 명세](d2s-state-actions-and-motion-v0.1.ko.md)에 상세 규칙과 수용 사례를 정의했다. 배포 결정에는 기업 SSO, 자료 보관 위치, 고객별 격리 수준과 목표 동시 사용량이 필요하다. 이 정보가 확보되기 전에는 현재의 모의 사례와 조건부 스택 권고를 유지한다.
